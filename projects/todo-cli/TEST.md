# 测试设计说明

## 测试文件
- `tests/test_todo.py`: 主测试文件，使用 pytest 框架

## 覆盖的验收标准
1. **添加任务**: `add_task` 函数测试验证添加任务后 `todos.json` 包含正确数据（ID=1，描述正确，状态为 pending），以及多次添加时 ID 递增。
2. **列出任务**: `list_tasks` 函数测试验证输出格式 `<id>: <description> [<status>]`，包括空列表、单任务、多任务场景。
3. **完成任务**: `done_task` 函数测试验证能正确更新任务状态，以及 ID 不存在时输出错误消息。
4. **错误处理**: 
   - 添加任务缺少描述时（通过 CLI 入口测试 `argparse` 输出用法错误）
   - 完成不存在的任务时输出错误消息
5. **数据持久化**: 测试验证通过 `load_tasks` 和 `save_tasks` 可以持久化存储任务数据。
6. **文件不存在处理**: `load_tasks` 在文件不存在时返回空列表。
7. **损坏文件处理**: `load_tasks` 在 JSON 解析失败时返回空列表（边界用例）。

## 测试策略
- 使用 `pytest.fixture` 在每个测试前后清理 `todos.json` 文件，确保测试独立性。
- 测试主要针对 PLAN.md 中定义的函数接口（`load_tasks`, `save_tasks`, `add_task`, `list_tasks`, `done_task`）进行单元测试。
- 对于 CLI 错误处理（`main` 函数中的 `argparse` 行为），通过模拟 `sys.argv` 和捕获 stderr 进行测试。
- 通过捕获 stdout 验证 `list_tasks` 和错误消息的输出内容。

## 边界用例与风险点
1. **空描述添加**: 虽然 SPEC 未明确要求，但测试中未包含添加空字符串描述的测试（`argparse` 会将其作为有效参数，但实际应用可能不希望接受空描述）。
2. **文件权限**: 未测试 `todos.json` 文件为只读或无写入权限时的行为。
3. **并发访问**: 未测试多个进程同时读写 `todos.json` 可能导致的数据损坏。
4. **输入验证**: 未测试任务描述中的特殊字符（如换行符、大量文本）对 JSON 序列化的影响。
5. **性能**: 未测试任务列表非常大时的性能表现。
6. **非标准库依赖**: 未直接测试 `todo.py` 是否导入非标准库（代码审查已完成，但测试未涵盖此静态检查）。
